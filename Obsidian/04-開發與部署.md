## 本機預覽

V1 頁面沒有編譯步驟，可從儲存庫根目錄啟動靜態檔案伺服器，再開啟：

`/system/index.html`

V2 為 Next.js 靜態匯出，開發預覽使用 `npm run dev:v2`；正式產物使用
`npm run build:pages` 建立於 `_site/`。

## 修改原則

- 維持既有繁體中文介面與視覺風格。
- 日期使用 `YYYY-MM-DD`，時間使用 `YYYY-MM-DD HH:mm`。
- 樓層名稱可能同時存在 `B1` 與 `B1F`，需先正規化。
- 新頁面需補齊導覽列、登入檢查、Supabase 初始化與跨頁連結。
- 不可刪除 `system/plans/` 圖資。
- `theme.js` 共用導覽的舊連結清理邏輯若只比對 href 檔名，遇到「不同用途但剛好連到同一個檔案」的頁面專屬連結會被誤刪（2026-08-04 踩過，`guardpatrol3d.html` 的「巡檢稽核總覽」曾被誤判成舊版「駐衛警巡檢」重複連結而消失）；新增清理規則時務必連結文字也一併檢查。
- 固定定位（`position:fixed`）搭配寫死像素偏移量（如 `top:62px`）的版面，一旦上方元素高度會變動（例如導覽列改成自動換行），要改用 CSS 變數＋ JS 量測實際高度同步，不能繼續假設固定高度。

## 驗證

- 檢查修改頁面的 inline JavaScript 語法。
- 測試登入保護、資料讀寫與錯誤訊息。
- 涉及 SQL 時確認舊環境也能套用。
- 部署後以版本查詢參數避開 CDN 快取確認結果。

## 部署

推送到 `main` 後，由 GitHub Actions 的 `Hardened Pages deployment` 進行正式建置、
來源簽章、全站掃描與 GitHub Pages 發布；Edge Function 只在相關檔案變更時由獨立流程部署。

### 2026-08-25｜CDN／WAF／Supabase 平台層攻擊偵測評估

#### 評估結論

- **應用層：部分完成。** V1／V2 頁面、登入與 Edge Function 已有伺服器端限流、資安告警、稽核與 LINE 投遞；RLS 仍是資料存取的最後邊界。
- **直接 REST：尚未納入應用層告警。** `system/api.html` 公開 `/rest/v1` 使用方式，直接呼叫 PostgREST 不會經過 `app-api`／`admin-api` 的應用層限流與事件寫入；必須改由 Supabase API Gateway 日誌與外部 WAF／限流規則觀測。
- **直接 Storage：分為兩種風險。** `repair-files`、`handover-attachments`、`vehicle-dispatch-files` 已是私有 bucket，並有系統權限、附件索引路徑、10 MB／MIME 防線；`floorplans` 依既有設計公開讀取，V1 2D／3D 頁直接使用 `/storage/v1/object/public/floorplans`，匿名下載與流量突增不會經過登入或 Edge Function。
- **未載入 JavaScript 的機器流量：目前只能在平台側看見。** 前端稽核事件不會產生，應以 API Gateway／Storage／Auth／Edge Function logs 的 IP、User-Agent、路徑、狀態碼、延遲與請求量建立偵測；Supabase Logs Explorer 可查 API 網路請求與 Storage 進出物件紀錄。
- **DDoS：本 repository 無法單獨完成。** 必須由 Supabase／上游 CDN 或自有 API 網域前的 WAF 吸收與封鎖；GitHub Pages 的靜態網站保護不會自動保護 `qztffronusdhgxhjjub.supabase.co` 的 REST／Storage 端點。

#### 建議處理順序（尚未執行的平台設定）

1. **P0｜可見性與基線**：在 Supabase Logs Explorer 開啟 API Gateway、Storage、Auth、Edge Function 來源，建立 4xx／5xx、未授權、單 IP 高頻、單路徑爆量與延遲門檻；先保存 7 日正常流量基線。Supabase 官方說明：[Logging](https://supabase.com/docs/guides/monitoring-and-debugging/logs)、[Storage Logs](https://supabase.com/docs/guides/storage/debugging/logs)。
2. **P0｜公開圖臺資產決策**：由業務確認 `floorplans` 是否含敏感圖資；若不應匿名取得，改私有 bucket＋短效 signed URL，並逐頁驗證 2D／3D、快取與失效流程。Supabase 私有 bucket 的存取模型：[Storage Buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals)。
3. **P1｜WAF／限流**：以自有 API 網域（或受控反向代理）承接 `/rest/v1/*`、`/storage/v1/*`、`/functions/v1/*`、`/auth/v1/*`，再套用 WAF managed rules、按 IP／API key／路徑的 rate limiting，以及對疑似機器流量的 challenge；規則需先以 7 日基線校準，避免誤傷正常巡檢與圖臺。Cloudflare 官方：[Rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/)、[Security features interoperability](https://developers.cloudflare.com/waf/feature-interoperability/)。
4. **P1｜無 JavaScript 監測**：建立低頻、固定來源的 synthetic probe，只做 HEAD／小型 GET／未授權 REST 檢查，不模擬大量攻擊；把 401／403、429、5xx、P95 延遲及流量突增送到既有告警通道。
5. **P2｜DDoS 與外部留存**：確認 Supabase 方案的日誌保留、Log Drain、費用上限與事件通報窗口；必要時以自有 WAF／CDN 供應商承接流量並做受控封鎖演練。Supabase Log Drains：[Log Drains](https://supabase.com/docs/guides/monitoring-and-debugging/log-drains)。

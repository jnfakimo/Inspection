# 資料保護技術基準（技術文件，非法律文件）

> **重要聲明**：本文件是給工程/維運人員看的技術盤點與技術層面準備，**不是服務條款、隱私政策或任何具法律效力的文件**。若業主要對客戶/員工提出正式的資料保護聲明或簽署合約，請另行諮詢律師；本文件只負責把「系統實際上存了什麼、怎麼存、能不能刪」講清楚，作為法律文件撰寫時的技術依據。

## 1. 系統儲存的個資欄位盤點

| 資料表 | 個資欄位 | 用途 | 誰能存取（依目前 RLS） |
|---|---|---|---|
| `users` | 姓名、電話、Email、部門 | 帳號身分、聯絡方式 | 任一已登入帳號可讀（見下方「已知取捨」）；只有管理員可寫 |
| `repair_requests` | 通報人姓名、電話、手機、部門 | 報修聯絡窗口 | 已登入帳號 |
| `handover_records` | 交接人／接班人姓名（關聯 `users`） | 交接紀錄 | 已登入帳號 |
| `vehicle_dispatch_requests` | 申請人姓名、電話、部門；司機姓名 | 派車申請與行車紀錄 | 已登入帳號 |
| `meeting_bookings` | 預約人（關聯 `users`） | 會議室預約 | 已登入帳號 |
| `checkin_logs` | 打卡人員（關聯 `users`）、打卡時間、地點 | 巡邏稽核 | 已登入帳號 |
| `audit_logs` / `case_status_log` / `users_history` / `audit_login_events` | 操作者、IP、User-Agent、變更前後內容 | 稽核軌跡 | 已登入帳號（讀）；系統寫入 |
| `client_error_logs`（本次新增） | 使用者 ID、瀏覽器資訊 | 錯誤診斷 | 僅管理員可讀 |

**不存在的個資類型**：系統不存密碼明文（登入走 Supabase Auth，密碼雜湊由 Supabase 管理，本系統資料庫內任何表都查不到密碼）；不存信用卡/金流資訊；不存生物特徵資料。

## 2. 資料留存原則（技術現況）

- 全站遵循 append-only：正式資料只能新增、修改、或把 `status` 改為 `inactive`，資料庫層有 trigger（`system/sql/permanent_data_protection.sql`）**強制禁止** `DELETE`/`TRUNCATE`，違反會直接被資料庫拒絕。
- 這代表：目前系統**沒有任何自動的資料留存期限機制**——理論上所有歷史資料會永久保存。
- 對內部 ERP／稽核系統而言，這通常是優點（稽核鏈完整、符合「不可竄改紀錄」的稽核要求）；但若業主未來面對員工個資保護的要求（例如「離職員工的聯絡方式不應無限期保留」），需要搭配下方第 3 節的去識別化機制處理，而不是直接刪除。

## 3. 離職人員個資去識別化（技術機制）

現況（本次已新增）：`system/sql/pii_deidentify.sql` 提供 `deidentify_departed_user(user_id)` 這個管理員限定的 RPC：
- 保留 `user_id`、`role`/`rbac_role`、`status='inactive'`、所有歷史稽核紀錄（`users_history`、`case_status_log` 等的 `operator_id`/`created_by` 等外鍵不受影響，稽核鏈完整性不受破壞）。
- 清除直接識別欄位：`name` 改為 `"已離職人員-" + 帳號末 4 碼`、`phone`/`email` 清空、`username` 改為不可登入的佔位值。
- 全程走 `users_history` 記錄這次去識別化操作本身（誰在什麼時候執行的），符合稽核要求。
- 只有 `is_admin()` 判定為真的帳號能呼叫，且執行前會檢查目標帳號必須已經是 `status='inactive'`（離職狀態），避免誤用來清除在職人員資料。

**使用方式**：後台 `rbac.html`／`admin.html` 帳號管理頁，對已停用帳號提供「去識別化個資」操作按鈕（見對應 commit）。

**限制**：這只處理 `users` 表本身的直接識別欄位；`repair_requests.reporter`／`vehicle_dispatch_requests.applicant_name` 等「當初填單當下留存的文字快照」欄位不會被連動清除（技術上可行，但涉及大量歷史資料回溯修改，风险較高，且會破壯資料原始性——例如報修單上「當初是誰通報的」本身也是稽核紀錄的一部分）。若業主有更嚴格的需求，需要另外討論這塊的取捨。

## 4. 存取日誌

- **寫入**已有完整記錄：`audit_logs`（設備/報修/維修等異動）、`case_status_log`（案件狀態流轉）、`users_history`（人員異動快照）、`audit_login_events`（登入/登出，含 IP、User-Agent）。
- **讀取**沒有記錄：系統目前不記錄「誰在什麼時候讀取/查看過誰的資料」。一般資料保護規範不強制要求記錄讀取，但若業主的客戶對此有特別要求，需要額外開發（例如在關鍵頁面的資料載入時額外寫一筆讀取記錄），本次未實作。

## 5. 待業主決策事項（非技術問題，本文件不代為決定）

1. 是否需要正式的隱私政策/服務條款——**需要律師撰寫，不是本系統的技術範圍**。
2. 離職員工個資去識別化的實際觸發時機（離職當下就做？還是保留一段緩衝期？）與核准流程（誰有權限按下這個按鈕）。
3. `repair_requests`／`vehicle_dispatch_requests` 等業務單據上的歷史文字快照是否也要納入去識別化範圍。
4. 是否要開始記錄「讀取」層級的存取日誌。

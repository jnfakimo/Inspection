# RDQ 需求規格：公文傳送流程

## 一句話任務
在 V2 建立以部室為單位的公文傳送、依序會辦、陳核簽收、核決與原申請人收訖紀錄子系統。

## ✅ 已確認
- 公文由公文管理人員建立，欄位至少包含公文主旨、公文編號；第一版不處理附件（Ⅰ／Ⅲ）。
- 單位公文管理人員每完成一個會辦單位後，再選擇下一個會辦單位；會辦完成後再選擇陳核單位（Ⅲ）。
- 陳核單位可由公文管理人員選擇任一核准單位；收文與核決可由同一人執行（Ⅲ）。
- 條碼只用於查詢公文，不直接觸發收文／簽收；退回一律回原申請人（Ⅲ）。
- 無條碼時可輸入公文主旨查詢；系統提供產生、下載或列印公文條碼功能，產生後仍不直接改變流程狀態（Ⅲ）。
- 每次送出、收文、會辦完成、簽收、核決、退回、收訖都要有不可刪除的時間軸紀錄（Ⅰ／Ⅳ）。
- 以部室與角色控管權限；目前包含單位公文管理人員、會辦收發人員、陳核單位人員、原申請人，並涵蓋副總簽收室、秘書室、總經理室等部室（Ⅰ）。
- 退回後原申請人可以補正並重新送出；原退回歷程保留，不覆蓋既有事件（Ⅲ）。
- 目標部室下拉只顯示第一階單位；流程節點仍以所選第一階單位承接（Ⅲ）。
- 公文編號由系統依臺北日期產生 `YYYYMMDD` 加三碼流水號；同日號碼已使用時自動取下一號，資料庫唯一索引與重試共同防止重號（Ⅲ）。
- 查詢條碼與公文編號使用同一值，不再另外輸入或產生不同條碼（Ⅲ）。
- 單位主管可查看本單位及下屬單位人員／公文；公文管理人可查看該範圍人員、建立及傳送公文；一般使用者僅查看本人送出的公文（Ⅲ）。

## ❓ 假設（未確認，已採預設值）
- 時間以伺服器時間保存、畫面以 Asia/Taipei 顯示；每筆事件保存操作者、角色、部室、動作與備註。
- 逾期門檻由後台依流程節點設定；第一版先提供通知承辦人與部室主管的設定位置。
- 同一公文可在不同階段由相同帳號執行，但每個動作仍須依當下部室／角色權限驗證。

## ➕ 已採納（象限Ⅳ）
- 不可刪除的完整流程時間軸。
- 防止重複掃描、重複收文與重複簽收的冪等控制。
- 逾期未收文或未核決時通知承辦人與主管。

## ❌ 排除項（明確不做）
- 第一版不做公文 PDF、附件、檔案版本與電子簽章內容管理。
- 第一版不做代理人／代理期間設定。
- 條碼掃描與主旨查詢都不直接改變流程狀態，必須進入公文後由人員確認操作。

## 📋 一段式需求規格
V2 新增「公文傳送流程」子系統，以部室為組織單位，讓公文管理人員建立只含**公文主旨**的公文，系統依臺北日期自動產生 `YYYYMMDD` 加三碼流水號，並將查詢條碼設為同一個公文編號；同日重號會自動跳下一號。公文管理人員再依序選擇第一階會辦單位；每完成一個會辦單位，管理人員再選擇下一個單位，會辦收發人員收文後執行會辦完成，全部會辦完成後由管理人員選擇任一第一階陳核單位送出。陳核單位人員收文／簽收後可由同一人核決，核決完成或退回均送回原申請人；原申請人可補正後重新送出，或收訖後結案，原流程歷程完整保留。單位主管可查看本單位及下屬單位人員與公文；一般使用者僅查看本人送出的公文。副總簽收室、秘書室、總經理室等部室與其人員由既有帳號／角色權限管理。每個送出、收文、會辦完成、簽收、核決、退回、補正重送、收訖動作均以伺服器時間記錄操作者、角色、部室、狀態、備註與前後狀態，不可刪除或覆寫；條碼可掃描查詢，查詢不得直接改變流程狀態；重複掃描或重複操作不得產生重複事件，逾期未收文／未核決時通知承辦人與部室主管。

## ✔ 驗收條件
- [ ] 依序會辦：前一單位未完成時，不可送下一個會辦單位或陳核。
- [ ] 每一階段均能正確記錄公文編號、部室、操作者、角色、動作與時間。
- [ ] 同一人可依權限完成陳核簽收與核決，但兩個動作仍分別留痕。
- [ ] 重複掃描、重複收文、重複簽收不會產生第二筆流程事件。
- [ ] 無條碼時可用公文主旨查詢，並可產生、下載或列印對應公文條碼。
- [ ] 退回、核決完成與原申請人收訖均能在歷程及狀態中查詢。
- [ ] 原申請人補正重送後，會產生新的送出事件，且不刪除原退回歷程。
- [ ] 逾期未收文／未核決會通知承辦人與主管，且通知本身也有紀錄。

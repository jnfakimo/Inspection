# RDQ 需求規格：電子交接簿現場調整版

## 一句話任務
以既有電子交接簿的流程為參考，另做一個可供現場逐步調整的現代化 Web 應用，支援手機、平板與電腦。

## ✅ 已確認
- 以現有系統為基礎，先做獨立頁面，驗證現場流程後再整合（Ⅰ／Ⅲ）
- 第一版以紙本欄位與簽核流程為主，保留報修、巡檢與設備異常串接入口（Ⅰ／Ⅲ）
- 流程以當班人員填寫及簽名、主管日後批示為主（Ⅰ／Ⅲ）
- 納入稽核軌跡、照片／附件、離線暫存與恢復連線補送、未交接／未簽核提醒（Ⅳ）
- 前端採 React／Next.js，負責 Dashboard、巡檢畫面、設備圖臺與手機操作介面（Ⅰ）
- 後端需要獨立 API 層，負責權限、流程、通知與資料分析；FastAPI 或 Node.js 尚待選定（Ⅰ）
- 資料層採 PostgreSQL；可優先評估 Supabase 以簡化部署（Ⅰ）
- 第一階段採 Supabase 直接提供資料、權限、檔案與 RLS API，不另建 FastAPI／Node.js 服務（Ⅲ）

## ❓ 假設（未確認，已採預設值，隨時可推翻）
- 紙本班次先以現場確認為準；照片中的 **08:00–10:00、10:00–18:00、18:00–02:00** 僅作初始參考→預設可由設定調整
- 紙本中的主任、副主任、組（副）長先視為批示／覆核角色，不在第一版固定成單一職稱→預設由權限與人員設定控制
- 新頁面沿用既有 Supabase 登入、RLS、主題與共用表頭→預設不另建帳號系統
- 新應用可與目前靜態 GitHub Pages 分開部署，透過 API／Supabase 與既有資料逐步整合→預設不直接把 Next.js 塞入現有 `system/` 靜態頁面
- 複雜通知或分析日後才視需要增加獨立後端→預設第一階段不維護兩套完整後端
- 離線資料先保存在裝置端，恢復連線後由使用者主動補送→預設不做多裝置同時編輯合併
- 第一版附件以照片與常見檔案為主，並受既有儲存空間與權限規則限制
- 提醒先做系統內待辦／狀態提醒，不預設寄送簡訊或電子郵件

## ➕ 已採納（象限Ⅳ）
- 保留不可任意覆寫的修改與簽核稽核軌跡
- 可在交接事項附加現場照片或檔案
- 支援斷線暫存與恢復連線後補送
- 對未交接、未簽核或逾時案件提供提醒

## ❌ 排除項（明確不做）
- 本階段不直接改寫既有 `system/handover.html` 的正式流程
- 第一階段不建立 FastAPI／Node.js 服務骨架；未來若需求變複雜，再以 API 邊界擴充
- 不在第一版把所有報修、巡檢、設備功能完整重做；只預留或驗證必要串接點
- 不把手機版硬做成紙本寬表格的縮小版
- 不預設加入簡訊、電子郵件、LINE 等外部通知

## 📋 一段式需求規格
請建立一個與既有靜態系統分開、可逐步整合的「電子交接簿現場調整版」Web 應用：前端採 **React／Next.js**，提供 Dashboard、巡檢畫面、設備圖臺與手機操作介面；第一階段由 **Supabase** 直接提供 **PostgreSQL、Auth、Storage、RLS 與資料 API**，不另建 FastAPI／Node.js 服務，並保留日後增加獨立後端的 API 邊界。應用需把照片中的紙本值勤／交接紀錄流程數位化：以可設定的班次、日期、當班人員、交接事項、主任指示、批示與簽核欄位為核心，讓當班人員可用手機或平板填寫及附加現場照片，主管可於日後批示；資料需支援草稿、送出、批示、完成與封存狀態，並保留每次修改與簽核的操作者及時間。第一版須能在斷線時暫存，恢復連線後補送，並對未交接、未簽核或逾時項目顯示提醒；桌機提供查詢與管理，平板提供整日班次看板，手機提供單班逐步填寫。需保留未來串接既有報修、巡檢與設備異常資料的 API／資料入口，但不在本階段重做這些子系統。完成後先交付可操作的介面與流程雛形，安排現場試用，再依回饋整合回正式電子交接簿。

## ✔ 驗收條件
- [ ] 手機、平板、桌機均能完成一筆紙本流程的填寫、暫存、送出與查詢
- [ ] 可附加照片／檔案，並看得到操作者、時間、狀態與修改／簽核紀錄
- [ ] 斷線時不遺失草稿，恢復連線後可補送，未完成交接／簽核會被提醒
- [ ] 現場人員能依紙本流程試用，並能在不改動正式頁面的情況下回收調整意見
- [ ] Next.js 前端與 API／PostgreSQL 資料層可在測試環境部署，且不影響既有正式靜態頁面

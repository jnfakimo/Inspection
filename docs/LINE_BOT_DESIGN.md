# 北農巡檢平台 LINE 機器人設計（草案）

> 狀態：設計草案（2026-10-31），尚未實作、未部署。
> 範圍：把目前「單一群組、純文字推播」的 LINE 通知，擴充為「群組＋個人、可查詢、依角色選單」的 LINE 機器人。

## 1. 目標與原則

- **對的人收到對的事**：指派給個人的事（派工、待批核、待驗收）推給個人；需要大家知道的事（急迫報修、巡邏逾時）推到對應的群組。
- **LINE 是通知與查詢入口，不是第二套系統**：資料與權限一律以平台為準。LINE 只負責提醒和快速查看，按「開啟系統」回到 V2 頁面處理。
- **權限即時判斷**：每次推播、每個查詢都重新檢查帳號狀態與 RBAC，不依賴綁定當時的權限。
- **去識別化**：LINE 訊息不放完整姓名、電話、照片，人名一律遮成「黃Ｏ發」。
- **預設關閉、逐項開啟**：沿用公務車個人通知的做法，所有新通知都有獨立開關、先用測試頻道驗收。

### 現況風險（建議先處理）

1. ~~**群組 ID 會被任意群組覆寫**~~（2026-10-31 已修正：改為後台產生一次性登記碼，在群組輸入「登記 XXXX-XXXX」才寫入，見 migration `20261031090000_line_group_register_codes.sql`）：webhook 收到「任何群組」的事件都會把 `line_group_id` 改成該群組（`vehicle-line-webhook.ts` 的 `saveGroupId`）。只要有人把機器人拉進另一個群組並說一句話，之後所有通知（含資安告警）都會送到那個群組。
2. **群組推播失敗就遺失**：群組通知直接呼叫 push，沒有 outbox 與重送，LINE 短暫失敗時訊息會消失，也沒有送達紀錄可查。
3. **所有通知擠在同一群組**：維修、駐警、資安訊息混在一起，收件人過多也增加訊息費用。

## 3. 頻道與收件對象

### 3.1 頻道

| 頻道 | 用途 |
|---|---|
| 北農巡檢通知（測試） | 開發與驗收，只加入測試人員 |
| 北農巡檢通知（正式） | 正式上線 |

兩個頻道的 secret／token 分開，測試環境絕不使用正式頻道。

### 3.2 通知群組（取代單一 `line_group_id`）

改成「通知路由」：每種通知對應一個路由鍵，每個路由鍵綁一個群組。

| 路由鍵 | 建議群組 | 收哪些通知 |
|---|---|---|
| `repair` | 維修調度群 | 新報修、急迫件、巡檢異常 |
| `guardpatrol` | 駐警隊群 | 巡邏逾時、駐警交接異常 |
| `handover` | 業管／市場管理群 | 交接簿異常案件、跨班未結事項 |
| `ops` | 資訊維運群 | 資安告警、錯誤門檻、推播失敗 |
| `meeting` | 總務群 | 會議室提醒 |

**群組登記改為明確授權**：
1. 管理員在「後台 → 系統設定 → LINE 推播」選擇路由鍵，按「產生群組登記碼」（6 碼、10 分鐘有效、一次性）。
2. 在目標群組輸入 `登記 123456`。
3. webhook 驗證登記碼後才寫入群組 ID，並在群組回覆「已登記為：維修調度群」。
4. 未登記的群組一律不寫入任何設定；機器人被移出群組（`leave` 事件）時自動停用該路由並通知 `ops`。

### 3.3 個人綁定（把公務車綁定擴充為全平台）

- 把 `vehicle_driver_line_bindings` 的流程抽成全平台共用的「LINE 帳號綁定」，所有同仁都可以綁定，不再限駕駛。
- 入口：「個人資料設定 → LINE 通知」，流程不變（網頁產生代碼 → LINE 傳代碼 → 開啟 accountLink 連結 → 完成）。
- 一個系統帳號只綁一個 LINE；一個 LINE 只綁一個系統帳號；可隨時解除。
- 帳號停用、離職或被移除權限時，自動停止推播並把圖文選單切回「未綁定」。
- 現有駕駛的綁定資料以 migration 轉入新表，不需重新綁定。

## 5. 訊息格式

改用 Flex Message 卡片，固定版型：

```
┌────────────────────────────┐
│▌🟠 派工給你               │  ← 左側色條依等級：紅／橘／藍
│ 第一市場 2F 配電盤旁       │  ← 標題：地點或主旨
│ 類型　電氣                 │
│ 報修　吳Ｏ美　10/31 09:12  │  ← 人名一律遮罩，時間一律台北時間
│ 案號　R-20261031-0012      │
│ [ 開啟案件 ]               │  ← 深連結到 V2 頁面
└────────────────────────────┘
```

- 每則都有純文字 `altText`，給手機通知列與不支援 Flex 的裝置顯示。
- 「開啟案件」按鈕連到 `https://jnfakimo.github.io/Inspection/v2/systems/...` 對應頁面；使用者在系統內照常登入與檢查權限。
- 不放照片、電話、完整姓名、內部備註。故障描述最多 60 字，多的截斷。
- 時間統一轉成 `Asia/Taipei`，避免出現 UTC 原始格式。

## 6. 圖文選單（依角色切換）

綁定或角色變更時，後端用 Rich Menu API 為該使用者連結對應選單。每份選單都是 2500×1686、6 格。

| 選單 | 對象 | 6 格內容 |
|---|---|---|
| 未綁定 | 尚未綁定的人 | 綁定說明、開啟系統、報修說明、聯絡管理員、（空）、（空） |
| 一般同仁 | 已綁定、無特殊角色 | 我要報修、我的報修、今日狀況、通知設定、開啟系統、使用說明 |
| 維修人員 | `workorder` 維修人員 | 我的工單、待接案件、我要報修、今日狀況、通知設定、開啟系統 |
| 主管 | 派工主管、交接簿批核主管 | 待派工、待我批核、今日摘要、逾期案件、通知設定、開啟系統 |
| 駐警 | `guardpatrol` 人員 | 本班巡邏進度、逾時巡邏點、駐警交接簿、我要報修、通知設定、開啟系統 |

- 一人有多種角色時，依「主管 > 維修人員 > 駐警 > 一般同仁」取最高的一份。
- 按鈕一律用 **postback**（例如 `a=my_orders`），不在聊天室留下文字。
- 「我要報修」「駐警交接簿」這類要填寫的功能，直接開 V2 對應頁面。

## 7. 查詢指令

使用者傳文字或按選單時，機器人用 reply token 回覆（不算推播額度）。

| 指令（文字或 postback） | 回覆內容 | 權限 |
|---|---|---|
| `今天` / 今日狀況 | 今日新報修數、處理中、急迫件；本日巡邏完成率 | 依可見系統顯示 |
| `我的工單` | 指派給我、未完工的工單（最多 5 筆＋「看全部」） | 維修人員 |
| `待派工` | 待派工清單（最多 5 筆） | 派工主管 |
| `待批核` | 待我批核的交接簿與公文 | 有批核權者 |
| `巡邏` | 本班巡邏點完成數、逾時點 | 駐警 |
| `摘要` | 昨日報修、完工、逾時、交接異常統計 | 主管 |
| `綁定 XXXXXX` | 個人綁定（沿用現有流程） | 所有人 |
| `解除綁定` | 回覆確認按鈕，確認後解除 | 已綁定者 |
| `說明` | 指令列表 | 所有人 |

- 未綁定的人只能用 `綁定`、`說明`。
- 群組內只回應 `登記` 與 `說明`，不在群組回覆任何個人資料。
- 看不懂的訊息回覆一次指令說明，同一人 10 分鐘內不重複回覆。

## 8. 寫入操作的界線

- **第一、二期 LINE 只讀**：接單、派工、驗收、批核一律回系統操作，不在 LINE 上執行。
- **第三期如果要在 LINE 上操作**（例如維修人員「接單」）：
  - 只開放低風險、可回復的動作。
  - 必須經過確認按鈕，postback 帶一次性動作碼（伺服器端產生、綁定使用者與案件、5 分鐘有效）。
  - 伺服器執行前重新檢查帳號狀態、權限、案件目前狀態，並寫入稽核紀錄（來源標記為 LINE）。
  - 批核、派工、刪除類動作不開放在 LINE 上執行。

## 9. 技術架構

```
業務事件（DB trigger / app-api / 排程）
        │  寫入
        ▼
  line_outbox（事件、收件人、等級、去重鍵、狀態）
        │  每分鐘
        ▼
  line-dispatch-worker ──push──▶ LINE
        ▲  lease / retry key / 退避重送

LINE ──webhook──▶ line-notify（簽章驗證）
                     ├─ 綁定／解除綁定
                     ├─ 群組登記（登記碼）
                     ├─ 查詢指令 → 查 DB（以綁定帳號身分＋RBAC）→ reply
                     └─ join / leave / unfollow 事件 → 更新狀態
```

- **outbox 一體化**：把 `vehicle_dispatch_line_outbox` 的做法擴充為全平台 `line_outbox`，所有推播（含現有群組通知）都先寫 outbox，再由 worker 送出。
  - 去重：`dedupe_key`（例如 `repair:{id}:dispatched`），同一事件只送一次。
  - 重送：沿用 `X-Line-Retry-Key`，失敗退避 1、5、15 分鐘，三次後標記失敗並通知 `ops`。
  - 送達紀錄：後台「通知中心」可查每則的狀態，不記錄訊息全文以外的 LINE 回應內容。
- **Webhook 分流**：`line-notify` 內依事件類型分派給 `binding`、`group-register`、`command`、`lifecycle` 四個 handler，各自有單元測試。
- **身分轉換**：webhook 只拿得到 LINE userId；先查綁定表得到 `user_id`，再用與 `app-api` 相同的權限函式判斷可見資料。查不到綁定就當作未登入。
- **金鑰**：channel secret 與 access token 都改放 Edge Function Secrets，不再存 `system_settings`；遷移期間兩邊並存，確認後移除資料表中的 token。
- **排程**：worker 沿用 GitHub Actions 每 5 分鐘呼叫的做法；🔴 危急類在寫入 outbox 後立即觸發一次 worker，不等排程。

### 新增或調整的資料表（草案）

| 資料表 | 用途 |
|---|---|
| `line_user_bindings` | 系統帳號 ↔ LINE userId（userId 另存雜湊供查詢），由 `vehicle_driver_line_bindings` 擴充而來 |
| `line_notify_routes` | 路由鍵 ↔ 群組 ID、啟用狀態、登記人與登記時間 |
| `line_group_register_codes` | 群組登記碼（只存雜湊）、路由鍵、到期時間 |
| `line_user_preferences` | 個人訂閱開關、勿擾時段 |
| `line_outbox` | 全平台推播佇列 |
| `line_action_tokens` | 第三期才需要：一次性動作碼 |

所有表都開 RLS、不授權前端直接讀寫，只能透過服務端 RPC；照專案慣例掛 `trg_prevent_removal`，以狀態停用不做實體刪除。

## 10. 訊息費用估算

- 回覆（reply）不計費；推播（push）依「則數 × 收件人數」計算，推到 20 人的群組算 20 則。
- 估算公式：`每月推播量 ≈ Σ(每日事件數 × 收件人數) × 30`。
- 降低用量的做法：
  - 群組精簡成員，只放需要處理的人。
  - 🔵 資訊類改為每日彙整一則。
  - 「指派給你」類只推個人，不另推群組。
- 實際方案級距與價格以 LINE 官方帳號後台當下公告為準，上線前用上個月的實際報修、巡邏逾時、交接筆數試算。

## 11. 分期

| 期 | 內容 | 驗收重點 |
|---|---|---|
| P0 風險修正 | 群組登記碼取代自動覆寫；token 移到 Secrets；現有群組通知改走 outbox | 機器人被拉進陌生群組不會改變設定；LINE 斷線後恢復會補送 |
| P1 個人通知 | 全平台綁定；派工給你、完工待驗收、待你批核、公文待辦；個人訂閱設定 | 只有權限內的人收到；停用帳號立即停止 |
| P2 選單與查詢 | 角色圖文選單；今天、我的工單、待派工、待批核、巡邏、摘要 | 查詢結果與系統畫面一致；未綁定者看不到資料 |
| P3 進階（選做） | 多群組路由完整化、勿擾彙整、低風險 LINE 上操作（接單） | 動作碼一次性、稽核紀錄完整 |

每一期都先在測試頻道驗收，再由管理員在正式環境逐項開啟。

## 12. 測試計畫

- 單元測試：簽章驗證、指令解析、postback 解析、路由選擇、去識別化、時間格式、去重與重送。
- 權限測試（PGlite，沿用 `test:vehicle-line-notifications` 的模式）：不同角色查詢結果、停用帳號、未綁定、群組內查詢被拒。
- 端對端：測試頻道實際收發，確認卡片版型、選單切換、深連結開啟正確頁面。
- 不以正式案件或正式群組做測試。

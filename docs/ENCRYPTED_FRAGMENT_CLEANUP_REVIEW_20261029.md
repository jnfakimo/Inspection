## 為何不能只掃描未引用片段並刪除

實際 encrypted-storage.ts 先逐段寫入，再發布索引；operations Map 只同步同一個 JavaScript 模組實例。鎖定的 AsyncStorage 2.2.0 原始碼顯示，JS 的 multiSet／multiRemove 各自呼叫原生操作，Android 的交易邊界也在各次操作內。應用程式目前沒有可涵蓋「讀索引、寫分段、發布索引、清理」的跨執行個體交易或互斥介面。

以兩次載入實際 TypeScript 模組建立獨立鎖與金鑰快取、共用持久化介面，控制非同步切換點，得到下列反例。這是儲存介面層的時序驗證，不冒充兩個 Android／iOS 原生程序實測。

| 候選清理方法 | 隔離反例 | 判定 |
|---|---|---|
| 掃描一次，刪除未被當前索引引用的片段 | 寫入者只完成第一段時停住；清理者刪第一段；寫入者恢復後發布缺段索引 | 不安全 |
| 重查索引兩次，確認沒有變更再刪 | 寫入者在兩次檢查期間均暫停，之後恢復，仍發布缺段索引 | 不安全 |
| 等待片段超過保存期限再刪 | 即使額外假設存在可信建立時間，模擬暫停超過 366 天後仍可恢復寫入，30 天門檻不能證明寫入已終止 | 不安全；現行片段也沒有建立時間欄位 |
| 刪除前最後一次重查 | 新分段已全寫好但索引尚未發布；重查後、刪除前另一執行個體發布；清理刪掉正在使用的新資料 | 不安全，檢查與刪除之間仍有競態 |
| 保留無法證明已廢棄的片段 | 相同暫停點不刪除；寫入恢復後完整新資料可解密讀回 | 本輪保留的防護；不是清理完成 |

測試中的不安全刪除程式只存在 test/storage.test.cjs 的反例，不會進入產品程式。成功的反例測試表示「已證明該方法會造成損壞」，不是清理方法通過驗收。

## 已修正：正常清理與另一讀取者交錯

另一個實際問題可在不新增刪除權限的情況下安全修正：讀取者先取得舊索引，另一模組正常完成新值發布或登出移除並清掉舊片段，讀取者接著讀舊片段會誤報「加密資料不完整」。修正前兩個情境均已重現。

現在缺片段時只重新讀取索引：索引確實改變才重新取得整組資料，最多三次；索引未變仍直接報錯。真正缺段不會改成空值，也不會回退舊明文。儲存介面錯誤繼續向上傳遞；新值仍經原有索引範圍驗證及 AES-GCM 驗證。連續變更超過上限回報重試錯誤，不無限迴圈。

本修正只處理上述讀取交錯，**不是跨執行個體全域鎖，也不授權回收未發布分段**。正常清理規則完全沿用既有程式，沒有新增 getAllKeys 掃描、TTL 刪除、清空儲存或金鑰輪替。

## 暫時不能修正的項目與防護

| 未完成項目 | 原因 | 現行防護與結案條件 |
|---|---|---|
| 未發布分段的自動回收 | 現有 API 無法區分已死亡寫入者與只是暫停的寫入者；逾時不是死亡證明 | 保留片段、禁止掃描式刪除。需由所有前景／背景讀寫者共同使用原生鎖或交易／fencing 機制，且程序死亡後可以安全接管 |
| 已被替換、但中斷前未清掉的舊分段 | 目前只有索引，沒有可驗證且持久的世代退役紀錄；任意未引用片段可能其實是準備中的新世代 | 保持 AES-GCM 加密、正常寫入及登出原有清理。後續需與前項一起設計持久日誌或原生交易，不能僅以名稱、年齡或兩次索引檢查判斷 |
| 殘片占用空間與保留期限 | 加密不代表不占空間，也不代表符合刪除期限 | 既有佇列限制及儲存失敗回報繼續有效；原生 SQLITE_FULL 已有前輪證據，但不能宣稱無限次中斷仍不耗空間，亦不能宣稱殘片已依期刪除 |
| 實體抹除及原生崩潰一致性 | 檔案系統／SQLite／Keystore 與硬體 flush 不由 JS 時序測試證明 | 待原生機制完成後，以隔離裝置測試多程序、鎖持有者死亡、斷電、空間不足與升級遷移；iOS 另需 Mac／Xcode／iPhone |

真正的完整修正需要原生儲存協調及相容遷移，不能只加一段 JavaScript 清理迴圈。離線維護也必須證明所有寫入者已停止、備份可恢復且不會重新啟動，單獨 SQLite 交易鎖不足以阻止另一程序之後發布先前寫好的索引；本輪不提供未達此條件的刪除指令。這是程式架構缺口，無需使用者手動刪除資料或更改密碼。
